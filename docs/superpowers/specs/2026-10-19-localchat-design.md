# LocalChat 首版设计

LocalChat 基于官方 LocalSend，服务于同一局域网内的个人多设备互传，以及不同人之间的聊天。首版目标是五个平台的一对一文字聊天、会话内传文件、自动发现设备和直接可见的 IP 地址。

## 已确认范围

- Fork 官方 `localsend/localsend`，名称为 LocalChat。
- Windows、macOS、Linux、Android、iOS 同等纳入产品范围。
- 纯局域网优先；接受手机打开应用时可靠通信，不要求锁屏后持续收消息。
- 自己的多台设备和不同人的设备，两种场景同样重要。
- 首版一对一聊天及文件传输，群聊后续加入。
- 自动发现在线设备，并直接显示 IP 地址。

## 基线与现状

远程 fork 为 <https://github.com/Jaron-admin/localchat>。本地开发分支 `localchat` 基于官方 `v1.18.2`，提交为 `af0416be50770a97760f7070684bc667b759a15c`。远程 `main` 保留 fork 时的上游代码；本地开发分支尚未推送。

继续使用 Apache-2.0，保留原有许可证、版权和适用的归属说明，修改内容标明变更。应用使用 LocalChat 名称与独立安装标识，不冒充官方版本。用户已于 2026-10-19 确认按此设计继续；目前完成源码准备，聊天功能尚未开发。

## 推荐架构

| 方式 | 取舍 |
| --- | --- |
| 给原版文字发送界面增加气泡 | 改动少，但文字占用文件接收会话槽，不能满足传文件时继续聊天。 |
| 在现有 HTTPS 服务增加独立消息接口 | 推荐；复用发现、证书、网络层和文件引擎，文字独立处理。 |
| 另建完整聊天服务或中心服务器 | 增加部署和维护成本，首版没有必要。 |

沿用 LocalSend 发现和文件协议，在现有服务增加 `/api/localchat/v1/` 命名空间。首版用 HTTPS 请求处理能力探测、聊天许可和文字投递，无需常驻 WebSocket。文件仍通过 `/api/localsend/v2/` 传输。

Flutter 负责界面、许可决策、数据库和状态展示；Rust core 负责协议、TLS 和传输；`localsend_isolates` 负责类型化事件和响应。扩展既有服务端事件及桥接，生成代码使用工具更新，遵循 Refena 和现有初始化顺序。

## 界面与日常使用

首页提供“聊天”“附近”“设置”。桌面宽屏使用会话列表与聊天内容双栏，手机从列表进入会话。保留现有文件选择、接收、传输状态和手动输入地址的能力。

附近列表与会话头部显示昵称、平台、当前 IP 和端口，标记是否支持聊天。页面显示本机局域网地址，多网卡时可展开全部地址。自动发现失败可手动输入 IP 和端口，但仍要验证对端身份。

首次聊天由接收方接受一次，之后按设备身份保存许可，可撤销或屏蔽。自己的设备可以在本机标记为“我的设备”；该分类不自动授予权限，也不代表跨设备账号。聊天许可与文件自动接收设置独立。

每个设备各自保存聊天历史。首版不自动把同一人的多台设备合并成一个联系人，也不自动同步所有历史。离线设备保留会话；发送文字先存入待发队列并显示尚未送达。

文件作为会话卡片显示，支持选择、接收或拒绝、进度、取消和打开。LocalChat 双方通过扩展元数据关联会话、附件及传输会话/文件 ID；原版设备继续使用兼容文件流程。只有文件实际写入成功才显示接收完成，不能把文字确认当作文件成功。首版不额外承诺新增断点续传。

## 发现与设备身份

发现设备后，使用绑定证书指纹的 HTTPS 连接查询 `/api/localchat/v1/capabilities`。原版设备返回不支持或 404 时仍可传文件，但不展示连续聊天入口。昵称或版本名称不能代替能力探测。

设备身份采用已验证的证书指纹，IP 只是当前地址。同一指纹换 IP 后延续会话；相同 IP 或昵称出现不同指纹时视为新设备，不继承许可或合并记录。证书重置后同样重新接受。

首次接受页展示昵称、平台、地址和可核对的指纹。广播仅提供发现线索；聊天要求 HTTPS 和实际客户端证书，服务端不能仅相信正文自报的身份。证书不匹配时停止发送，不退回明文。

## 消息可靠性

每条消息生成固定随机 `messageId`，携带协议版本、正文和发送时间。发送时间用于显示，不能作为身份或去重依据。发送方先保存待发消息，再发网络请求。

接收方把正文和去重键 `(senderFingerprint, messageId)` 在同一数据库事务中提交后才确认送达。重复请求返回已有确认，不重复产生气泡或通知；同一 ID 携带不同内容时拒绝。磁盘满或数据库写入失败时不确认成功。

界面区分“待发送”“发送中”“已送达”“未确认”和明确失败或拒绝。“已送达”只代表对方已保存，不代表已读。超时可能发生在对方保存之后，因此自动和手动重试都复用原 ID。

恢复前台或重新发现设备时检查待发消息；一次投递周期最多自动重试 3 次并退避，此后显示未确认并允许手动重试。退后台暂停时不宣称持续在线；恢复后重新发现、校验证书和地址。无法局域网直连时不通过云端补投。

正文限制为 32 KiB UTF-8；邀请、请求和队列有容量及并发限制，过载返回明确错误。聊天队列和状态独立于原版文件接收槽：上传中、等待文件确认或拒绝文件均不能阻止已许可的文字聊天。文件事件也不能长期占满消息处理能力。

## 本地数据

使用独立 SQLite 数据库，不把会话塞进现有仅保留少量接收历史的设置项。实施计划核验数据库适配库的五平台支持情况。

| 数据 | 内容 |
| --- | --- |
| peers | 指纹、昵称快照、平台、最近地址、本机分类、许可状态。 |
| conversations | 本地会话 ID、对端指纹、创建时间与最近活动。 |
| messages | 消息 ID、会话、方向、正文、发送/接收时间、投递状态；接收去重键设唯一约束。 |
| attachments | 关联消息、传输会话和文件 ID、名称、大小、本地路径与状态。 |

## 独立安装与平台要求

LocalChat 使用独立应用 ID、安装器 ID、进程实例标识、配置目录、证书和数据库，避免覆盖 LocalSend。Windows 安装脚本必须去掉针对原版 LocalSend 的卸载逻辑。首版不自动迁移原版设置和证书。

正确处理 TCP 监听端口占用，公告并使用实际端口；UDP 发现保持协议兼容。与原版同时运行时的发现与互传需要验证，不能仅靠更名认定兼容。

五个平台均须构建和实机验收。iOS/macOS 构建签名和系统权限分别处理；手机前台恢复后重新建立连接，不承诺 iOS 锁屏后台常驻。已找到 D:/flutter 下的 Flutter 3.47.5，与仓库固定的 3.41.9 不同；尚未运行应用构建。

## 验收标准

1. 五个平台可构建启动，覆盖桌面与手机之间的发现、双向文字和文件互传。
2. 附近列表与会话直接可见 IP；多网卡及 IPv6 地址保留必要作用域信息。
3. 传大文件或等待文件确认时仍能双向聊天。
4. 重启保留会话与待发消息；确认丢失后重试不产生重复记录。
5. IP 变化延续原会话；IP 被其他身份接替、证书不匹配或重置时不向错误身份发送正文。
6. 写入失败、队列满、许可拒绝及网络中断都准确显示，不误报送达。
7. 手机恢复前台后重新发现和投递，离线时状态符合实际。
8. 与原版 LocalSend 互传文件通过回归，原版不被误认成聊天客户端。
9. 安装、升级、卸载 LocalChat 均不修改原版程序和数据。

验证包括 Rust 协议及 TLS 集成测试、持久化与去重测试、关键 Flutter 界面测试、五平台构建和实机联调。Rust core 使用 `--features full`；Flutter 使用仓库固定版本。这些是验收要求，不表示当前已经通过。

## 开发顺序

先验证原版构建基线及独立安装，再做消息协议和持久化，随后接入聊天界面及文件卡片，最后完成五平台互通、权限和恢复验收。群聊在一对一稳定后单独设计成员身份和消息分发。
